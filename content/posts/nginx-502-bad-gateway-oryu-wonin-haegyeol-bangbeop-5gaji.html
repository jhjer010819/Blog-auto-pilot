Nginx가 앞단에서 요청을 받아 뒤쪽 서버로 넘기는 프록시로 동작할 때, 뒤쪽 서버(업스트림)에서 올바른 응답을 받지 못하면 클라이언트에게 502 Bad Gateway를 돌려줍니다. 업스트림 서버를 고르지 못한 경우에도 상태 값은 502가 됩니다. 먼저 오류 로그를 확인하고, 뒤쪽 서버가 켜져 있는지, 주소와 소켓 경로가 맞는지, 소켓 권한이 있는지, 대기 시간이 너무 짧지 않은지를 살펴본 뒤 설정을 고치고 nginx -t로 검사한 다음 다시 적용하는 것이 기본 순서입니다.

502 Bad Gateway의 의미

공식 문서에 따르면 Nginx는 요청을 받아 뒤쪽 서버로 넘기고, 그 응답을 받아 클라이언트에게 보냅니다. 뒤쪽 서버가 꺼져 있거나 주소가 잘못되어 연결되지 않거나, 연결은 되었지만 올바른 응답을 주지 못하면 이 과정이 깨집니다. 여러 서버를 upstream 그룹으로 묶으면 기본적으로 서버 가중치에 따라 요청을 나누고, 한 서버와 통신 중 오류가 나면 요청을 다음 서버로 넘기지만, 어떤 서버에서도 성공한 응답을 얻지 못하면 클라이언트는 마지막 서버와의 통신 결과를 받게 됩니다.

오류 로그에서 원인 확인

원인 확인은 오류 로그를 살펴보는 일부터 시작합니다. error_log의 기본값은 logs/error.log이고 기본 수준은 error이며, 입문 안내에서는 로그 파일이 /usr/local/nginx/logs 또는 /var/log/nginx 아래에 있을 수 있다고 안내합니다. 리눅스에 패키지로 설치한 환경에서는 /var/log/nginx/error.log를 흔히 쓰지만, 정확한 경로는 설치 방식에 따라 다를 수 있으므로 nginx -V로 컴파일할 때 지정된 값을 확인할 수 있습니다.

로그에 connect() failed와 함께 오류 번호 111, Connection refused가 보이면, 해당 주소와 포트에서 받아 주는 프로세스가 없거나 연결을 거절한 경우가 많습니다. upstream prematurely closed connection이 보이면, 뒤쪽 서버가 올바른 응답을 끝까지 보내기 전에 연결을 닫은 것입니다. 메시지에 적힌 업스트림 주소를 설정과 맞춰 보시기 바랍니다.

원인과 해결 방법 5가지

방법 1. 업스트림 서버 동작 여부 확인

502의 흔한 원인은 뒤쪽 서버가 꺼져 있거나, 설정한 주소와 포트에서 요청을 받지 않는 상태입니다. HTTP 프록시라면 proxy_pass가 가리키는 대상(예: http://localhost:8000)이 실제로 켜져 있는지 확인하고, PHP라면 FastCGI 서버(예: localhost:9000 또는 유닉스 소켓)가 동작 중인지 확인합니다. 서버가 내려가 있다면 서비스를 다시 올린 뒤, 같은 주소에서 요청을 받고 있는지부터 살펴보시기 바랍니다.

upstream 블록의 server에서 max_fails의 기본값은 1이고, fail_timeout의 기본값은 10초입니다. 이 시간 안에 실패한 횟수가 기준에 이르면 그 서버는 같은 시간 동안 사용하지 않으며, 그룹에 서버가 하나뿐이면 이 값은 무시되어 해당 서버를 사용할 수 없는 상태로 보지 않습니다.

방법 2. 주소와 포트, 소켓 경로 확인

뒤쪽 서버는 켜져 있는데 주소가 어긋나도 연결은 실패합니다. proxy_pass에는 http://localhost:8000처럼 도메인이나 IP와 포트를 쓰거나, 아래처럼 유닉스 소켓 경로를 쓸 수 있습니다.

proxy_pass http://unix:/tmp/backend.socket:/uri/;

fastcgi_pass는 localhost:9000 또는 unix:/tmp/fastcgi.socket 형식을 쓰고, upstream 블록의 server에서 포트를 생략하면 80번을 사용합니다. PHP-FPM의 listen 값(IP와 포트, 또는 유닉스 소켓 경로)과 Nginx의 fastcgi_pass가 같은 대상을 가리키는지 확인하고, 소켓 파일 이름이나 디렉터리만 달라도 연결이 거절될 수 있으니 경로를 한 줄씩 맞춰 보시기 바랍니다.

방법 3. PHP-FPM 소켓 권한 확인

같은 기기에서 웹 서버와 PHP-FPM을 쓸 때 PHP 공식 문서는 유닉스 소켓을 권장합니다. 리눅스에서는 listen.owner, listen.group, listen.mode로 소켓 접근을 제어하며, 웹 서버가 연결하려면 읽기와 쓰기 권한이 필요합니다. 소유자와 그룹의 기본값은 실행 중인 사용자이고, 모드의 기본값은 0660입니다.

Nginx 작업 프로세스가 쓰는 사용자에게 소켓 읽기·쓰기 권한이 없으면 연결이 막힐 수 있습니다. 소켓 소유자와 모드를 웹 서버 사용자가 읽고 쓸 수 있게 맞춘 뒤, 바뀐 풀 설정이 실제로 반영되었는지 확인하시기 바랍니다.

방법 4. 타임아웃과 버퍼 크기 점검

뒤쪽 서버가 응답을 보내는 데 시간이 걸리면, 대기 시간이 지나 연결이 끊길 수 있습니다. proxy_connect_timeout, proxy_read_timeout, proxy_send_timeout의 기본값은 모두 60s이고, FastCGI의 fastcgi_connect_timeout, fastcgi_read_timeout, fastcgi_send_timeout도 기본값은 60s입니다. proxy_read_timeout과 fastcgi_read_timeout은 응답 전체가 아니라 이어지는 읽기 사이 간격에만 적용되고, proxy_send_timeout과 fastcgi_send_timeout은 이어지는 쓰기 사이 간격에만 적용되며, proxy_connect_timeout은 보통 75초를 넘기기 어렵습니다.

응답 앞부분을 읽는 proxy_buffer_size의 기본값은 메모리 페이지 크기인 4k 또는 8k이고, 이 크기를 넘기면 응답이 잘못된 것으로 봅니다. proxy_buffers의 기본값은 8 4k|8k입니다. 처리에 시간이 오래 걸리는 요청이라면 대기 시간을 늘릴 수 있고, 응답 헤더가 큰 경우에는 버퍼 크기를 공식 문서 설명에 맞게 조정할 수 있습니다.

proxy_connect_timeout 60s;
proxy_read_timeout 60s;
proxy_send_timeout 60s;

연결 오류나 시간 초과가 나면, proxy_next_upstream의 기본값인 error timeout에 따라 요청을 다음 서버로 넘길 수 있습니다. 다만 응답을 클라이언트에게 이미 보내기 시작한 뒤에는 다음 서버로 넘길 수 없습니다.

방법 5. 설정 검사와 재적용

설정을 고친 뒤에는 바로 재시작하지 말고, 먼저 nginx -t로 문법과 설정이 가리키는 파일을 열 수 있는지 검사합니다. 설정 파일의 기본 이름은 nginx.conf이고 위치는 /usr/local/nginx/conf, /etc/nginx, 또는 /usr/local/etc/nginx일 수 있어서, 다른 파일을 쓰려면 -c로 경로를 지정하면 됩니다.

검사가 끝나면 nginx -s reload로 설정을 다시 읽히면 되며, 마스터 프로세스는 새 설정의 문법을 확인한 뒤 새 작업 프로세스를 시작하고 이전 작업 프로세스는 하던 요청을 마친 뒤 종료합니다. 새 설정을 적용하지 못하면 기존 설정을 그대로 유지하므로, 적용 후에도 오류 로그를 다시 확인해 보시기 바랍니다.

마치며

502 Bad Gateway는 Nginx가 뒤쪽 서버에서 올바른 응답을 받지 못했거나, 업스트림 서버를 고르지 못했을 때 나타납니다. 오류 로그의 메시지와 주소를 먼저 보고, 서버 동작 여부, 주소와 소켓 경로, PHP-FPM 소켓 권한, 타임아웃과 버퍼를 점검한 뒤 nginx -t로 검사하고 nginx -s reload로 반영하시기 바랍니다.

본 글은 정보 제공을 목적으로 작성되었으며, Nginx와 PHP-FPM의 설정 값과 기본값은 버전과 설치 방식에 따라 다를 수 있습니다. 운영 중인 서버의 설정을 바꾸기 전에는 설정 파일을 백업하고, 적용 전에 nginx -t로 검사하시기 바랍니다.
